# 客户端更新与旧版本停用

启动时独立检查客户端更新，不依赖整合包 manifest 下载成功。发现新版会自动弹窗；同一次运行中
对同一版本点“稍后”不会反复弹出，可在“设置 → 更新 → 检查更新”重新打开。
游戏、整合包安装或账户授权进行中会延后显示，不会强行结束正在运行的游戏。

下载进度、签名校验与失败重试都在更新弹窗中。只有签名校验通过才启动 NSIS；
下载中断不替换现有客户端。应用层与 native 层分别防止重复安装。

## 策略

修改 `client/update-policy.json`，然后发布新版，或对现有 latest 重新 promote 即可更新策略。
无需修改历史安装包或重新打包客户端；`latest/metadata.json` 是线上指针和策略来源。

示例（仅作说明，不代表当前生产策略）：

```json
{
  "minSupportedVersion": "1.1.5",
  "blockedVersions": ["1.1.8"],
  "reason": "旧版本包含影响正常使用的问题，请更新。"
}
```

假设 latest 为 1.2.0：低于 1.1.5 的旧版，以及单独列出的 1.1.8 必须升级；
1.1.5、1.1.6、1.1.7、1.1.9 可以稍后更新。`null` 门槛和空列表表示没有停用版本。
版本比较遵循 SemVer，忽略 build metadata。

```powershell
# 修改策略后，将当前已发布版本重新设为 latest（这里版本号按实际填写）
.\client\promote.ps1 -Version 1.2.0 -WhatIf
.\client\promote.ps1 -Version 1.2.0
```

强制更新弹窗只允许“立即更新”或“退出客户端”，关闭按钮、Escape 和背景点击不能继续使用旧版。
更新失败保留“重试 / 退出”。游戏启动和整合包准备流程也会在下载/写入前检查策略，
并非只禁用前端按钮。已运行的游戏不会被突然结束。

发布器禁止把 latest 指向低于最低支持版本或被停用的版本，避免形成无法完成的强制更新循环。
回滚时也会重新应用当前策略，不能用历史元数据意外恢复过时的支持门槛。

## 版本边界

此交互与策略由 1.1.5 起实现。已经安装的 1.1.4 不会因为发布元数据改变而获得新的界面，
从 1.1.4 升级至 1.1.5 仍使用旧界面；装好 1.1.5 后的后续更新才使用新弹窗。
旧版仅识别 `mandatory` 的能力不等于支持按版本门槛停用。
这是正常客户端的版本支持控制，不是防止被修改客户端接入的服务端安全认证。
